# S07: provider runtime, ownership and recovery

Implemented October 24, 2026 in the isolated refinement worktree, starting at `6a29b00`. S05/S06 accounting, query and configuration authorities remain intact. App version is now `0.7.0`. This session does not add a server, database, dashboard or credential-management workflow.

## Runtime boundary and refresh policy

[usage_runtime.py](../windows/usage_runtime.py) owns `ProviderState`, immutable `ProviderView`, `PollingRuntime` and `RuntimeOwner`, without importing the tray, GUI libraries or report renderers. The tray re-exports `ProviderState` for existing callers. Provider adapters stay in [usage_core.py](../windows/usage_core.py); local report queries still use the independent headless S05 service.

There is one worker, fetch lock and wake event per selected provider. `PollingRuntime.start()` is idempotent; `refresh()` signals every provider independently. No worker can consume another provider's wake signal. The state checks its own monotonic deadline and nonblocking fetch lock before starting a request, so repeated Refresh actions cannot bypass cooldown/backoff or create simultaneous same-provider requests. Workers sleep until their own eligible deadline or a wake/stop signal; they no longer wake/redraw every second. Extremely long Retry-After values use bounded daily wait slices while retaining the full eligibility deadline.

Success schedules the next eligible check at least 300 seconds after completion. Consecutive failures use 300/600/1200/2400-second delays, respecting a longer finite provider Retry-After. Success clears the failure count. The monotonic deadline exists only in process memory. `ProviderView.retry_at` is derived as current wall time plus remaining monotonic delay for display; it is not a persisted scheduling timestamp. Wall-clock changes therefore adjust the displayed absolute retry time without permitting an early request. Restart creates a new in-memory schedule; no cross-restart cooldown persistence is claimed.

Views distinguish outcome categories from current phase. Known categories include waiting, success, blocked, login_required, network_error, cooldown, unsupported_response, unexpected_local, cancelled and generic provider_error where the adapter cannot identify the remote cause safely. Phases are due, refreshing, cooldown or stopped. Adapter categories come from known error branches, never substring classification of arbitrary exception text or remote bodies. A generic Codex RPC error remains generic rather than asserting a particular authentication/network cause. Existing sanitized adapter messages are preserved; unexpected exceptions receive a static message. One-shot error JSON adds the safe category. Codex's explicit ordinaryUsageAllowed=false produces a blocked snapshot independently of remaining percentages; its tray indicator is red and the note remains visible.

The last successful snapshot is retained through a failed request, with its original checked time and an explicit stale warning. Runtime snapshots copy legacy window lists into tuples so consumers cannot mutate accepted state through the original list. A stopped runtime does not accept a late completion as a fresh snapshot. None of this establishes local-history account matching or quota history.

The tray's renderer waits for state/report-status notifications, coalesces them and redraws only then. Refresh start/end and report activity are meaningful changes; cooldown-only manual wakes do not generate redraw notifications. This removes the previous once-per-second redraw loop without changing terminal/report styling.

## Installation ownership

The normal tray entry point and real `--once` checks acquire `%LOCALAPPDATA%\UsageTray\runtime.lock` (the S06 fallback directory applies when LOCALAPPDATA is absent). It is an OS-owned byte-range lock with no PID, credentials, snapshots or scheduling state stored in the file. The file is deliberately retained after release; deleting/recreating a locked filename could produce a competing file identity. Closing the handle releases ownership, including OS cleanup after process death. Windows can have a brief release gap after abrupt termination; acquisition retries for at most 250 ms before reporting contention.

A second owner exits **3**, with a safe already-running message when stderr is available. It does not start GUI/provider workers, change the first instance's provider/configuration, or kill an existing process. All checkouts and alternate configs using the same application-data folder share this owner. Different LOCALAPPDATA folders are explicitly different installations; no machine-wide/account-wide exclusivity is inferred. The supported contract assumes a normal local filesystem, not adversarial lock-file replacement or network-share locking.

Offline `--report`, settings/version/diagnostic commands and `--once --demo` require no polling owner and remain available while the tray runs. Real `--once` holds the owner for its explicit one-shot operation and is rejected if the tray owns it; sequential explicit one-shot invocations do not inherit another process's in-memory cooldown. Programmatic helpers assume their caller provides process ownership; the production CLI entry point enforces it. Changing an existing tray's settings requires Quit/restart; a second launch is not an IPC configuration mechanism.

## Shutdown and owned process containment

Quit sets the stop event, wakes every provider and renderer, stops the native icon loop and then joins provider workers for a shared maximum of 30 seconds. The renderer has a two-second join and an active report job a one-second join. Reports check stop before saving/opening after a query, so Quit suppresses a pending viewer launch when it observes stop. Local filesystem IO already in progress is not forcibly cancelled. Arbitrary Python fetch functions cannot be forcibly killed safely; `PollingRuntime.close()` explicitly returns false if a worker outlives the bounded join, and workers are daemon threads. The supported Codex adapter is cancellable; Claude retains its existing 25-second socket timeout, with cancellation checks before/after the request. A socket timeout is not a total HTTP-response deadline, and this session does not claim hard cancellation of every possible slow HTTP/filesystem operation.

Codex RPC queue waits check cancellation every 100 ms. Cancellation, timeout, normal exit and initialization failure all close the app-owned process tree through [usage_process.py](../windows/usage_process.py). On Windows, a hidden child starts suspended, is assigned to a job with kill-on-close, and is resumed only after containment succeeds. This covers an npm/node launcher and its native descendants. Failure to establish containment terminates the still-suspended child and fails safely before its code runs. Normal cleanup terminates that job, waits up to three seconds for zero active processes, closes its handle and waits for the direct process. Abrupt parent death closes the job handle through the OS. No user CLI process is discovered or terminated by name, and no unrelated PID tree is targeted.

The implementation follows Microsoft's [job assignment contract](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [suspended-thread resume contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread), [job termination](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject), and [active-process accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information). Windows 10/11 is the verification target; the POSIX process-group fallback is not a claim of macOS app verification. Unsupported Windows job restrictions fail closed with a safe local error. Existing credential redirect protection, CLI-managed authentication and read-only Claude credential handling remain unchanged.

Explicitly opened terminal/browser report viewers are handed to the user and may remain after Quit. They are not polling workers; the app does not forcibly close a terminal/browser the user is reading. No login-session, source history or user-owned provider process is cleaned up on shutdown.

## Report failures and bounded artifact retention

[usage_failures.py](../windows/usage_failures.py) maps report failures to static categories/messages with query/save/open phases: permission_denied, disk_full, io_error, invalid_data, unexpected_local and open_failed. Parsing/calculation/viewer failures are no longer all labeled as folder permissions. A viewer launch failure preserves the saved file; CLI exits nonzero and reports the open failure. Shell paths remain data arguments, preserving the existing safe PowerShell terminal launch. Launch success is not proof that an external viewer subsequently rendered the file.

[usage_artifacts.py](../windows/usage_artifacts.py) reserves `UsageTray/Reports/Generated` for new automatic reports. After a successful automatic save, prune matching regular report files to the newest **100**, and remove those older than **30 days**, while protecting the just-created file and counting it toward the cap even after a wall-clock rollback. It is a count/age policy, not a byte quota or guarantee under IO failures. Handled retention failure produces a static warning and preserves the successfully saved report. Automatic terminal stdout reports produce no file.

Only fixed-format `usage-YYYYMMDD-HHMMSS-<8 random characters>.txt/.html` files in this application-owned folder qualify. Cleanup is nonrecursive, checks resolved containment, excludes links/reparse files and refuses linked/junction report directories. Do not put manually managed files in this reserved generated folder. Explicit `--output` exports must use another folder; they are not automatic retention candidates. Legacy files directly under Reports, unknown filenames, nested directories, source histories, credentials and build artifacts are never pruned by this policy. The folder menu still opens Reports so previous reports remain accessible. No existing real report/history cleanup was run during implementation; all retention checks use temporary synthetic artifacts.
